Guia Git — Trabalho em Equipe e Integração

Guia prático para entender branches, commits, push, Pull Requests, conflitos e diagnóstico dos principais problemas encontrados durante o desenvolvimento colaborativo.

Git • GitHub • Integração

🎯 Objetivo

O objetivo deste guia é ajudar você a compreender o que está acontecendo com o código durante o trabalho em equipe. O roteiro de desenvolvimento mostra o passo a passo da atividade; este guia explica os conceitos e como investigar problemas quando algo não acontece como esperado.

1. Por que não trabalhar todos na main?

A main representa a versão principal que deve permanecer estável. Se vários grupos alterarem diretamente a mesma branch, aumenta o risco de código incompleto, sobrescrita de alterações e conflitos.

Por isso, o projeto utiliza uma estrutura em que as funcionalidades são desenvolvidas em branches próprias e posteriormente integradas em develop.

2. O que é uma branch?

Uma branch é uma linha independente de desenvolvimento dentro do mesmo repositório. Ela parte de um ponto existente do projeto e permite que uma equipe faça alterações sem modificar imediatamente a versão principal. 

main
 │
 └── develop
      │
      ├── feature/grupo-01-manutencao
      ├── feature/grupo-02-combustivel
      ├── feature/grupo-03-ocorrencias
      └── feature/grupo-04-sla

No laboratório, cada grupo deverá trabalhar em sua própria feature/....

3. O que é um commit?

É um registro no histórico do Git dizendo quais alterações foram gravadas naquele ponto. 

git add .
git commit -m "Implementa controle de manutenção"

git add prepara as alterações. O git commit registra uma versão no histórico local.

Commit não é push. O commit registra localmente; o push publica no GitHub.

4. O que é push?

É o envio dos commits da branch local para o GitHub.

git push -u origin feature/grupo-01-manutencao

Depois do push, a branch fica disponível no repositório remoto para revisão e para a criação do Pull Request.

5. O que é Pull Request?

É uma solicitação para incorporar o trabalho de uma branch em outra. No nosso projeto: 

feature/grupo-01-manutencao
              ↓
          Pull Request
              ↓
           develop

O Pull Request permite revisar arquivos, discutir alterações, verificar testes e decidir quando a funcionalidade está pronta para integração.

Confira: na prática, o destino do Pull Request é develop, não main.

6. Processo completo do grupo

  1. Atualizar develop.
  2. Criar a branch do grupo.
  3. Implementar somente o requisito recebido.
  4. Executar a aplicação.
  5. Testar a funcionalidade.
  6. Verificar git status.
  7. Conferir as alterações com git diff.
  8. Adicionar os arquivos com git add.
  9. Criar um ou mais commits coerentes.
  10. Enviar a branch com git push.
  11. Abrir o Pull Request para develop.
  12. Aguardar revisão e realizar correções, se necessárias.
  13. Após aprovação, realizar o merge.

7. Comandos de diagnóstico: primeiro descubra, depois corrija

Quando algo não funcionar, não execute vários comandos aleatoriamente. Primeiro descubra o estado do repositório.

git status — Qual é o estado do projeto?

git status

Mostra a branch atual, arquivos modificados, arquivos preparados para commit e situações que exigem atenção.

git branch — Em qual branch estou?

git branch

A branch marcada com * é a branch ativa.

git diff — O que foi alterado?

git diff

Permite revisar as diferenças no código antes de preparar as alterações com git add.

8. Situações comuns e como resolver

Durante a prática, mensagens de erro fazem parte do processo de aprendizagem. A sequência recomendada é: 

mensagem
   ↓
diagnóstico
   ↓
identificar a causa
   ↓
executar a correção
   ↓
testar novamente

🔵 8.1 Não sei em qual branch estou

git branch

Confirme se o * está na sua branch feature/.... Se estiver em outra branch, não continue alterando o código até corrigir o fluxo.

🟡 8.2 Minha develop está desatualizada

git fetch origin
git checkout develop
git pull origin develop

Atualize a develop antes de criar uma nova branch de funcionalidade.

🟠 8.3 Não sei o que alterei

git status
git diff

Primeiro identifique os arquivos modificados; depois confira as diferenças.

🟣 8.4 Fiz commit, mas a alteração não aparece no GitHub

O commit fica no histórico local. Para publicar a alteração: 

git push
Resumo: commit = histórico local; push = publicação no GitHub.

🔴 8.5 Erro 403 ou permission denied

remote: Permission to ... denied
fatal: unable to access ...

A conta utilizada pode não possuir permissão de escrita no repositório ou branch.

Procedimento: pare e informe o professor. Não tente contornar a permissão.

🟤 8.6 Pull Request com destino errado

Confira os campos:

base: develop
compare: feature/grupo-01-manutencao
O fluxo da prática é feature → Pull Request → develop.

🟢 8.7 O Pull Request recebeu uma solicitação de correção

Continue na mesma branch. Faça a correção, teste e publique novamente: 

git status
git diff
git add .
git commit -m "Corrige validação da funcionalidade"
git push

O Pull Request existente será atualizado automaticamente.

⚠️ 8.8 Apareceu um conflito

Conflito acontece quando o Git não consegue combinar automaticamente duas alterações. Primeiro identifique os arquivos: 

git status

No arquivo em conflito, o Git poderá apresentar marcadores como: 

<<<<<<< HEAD
versão atual
=======
versão da outra branch
>>>>>>> outra-branch

Abra o arquivo no VS Code, compare as versões, resolva a combinação, teste a aplicação e só então registre a resolução. 

git add .
git commit -m "Resolve conflito de integração"
git push
Em caso de dúvida: não apague blocos de conflito sem entender o que representam. Pare e peça orientação ao professor.

9. Tabela rápida — “apareceu isso, faça aquilo”

Situação Primeiro procedimento Objetivo
Não sei minha branch git branch Identificar a branch ativa.
Develop desatualizada git pull origin develop Atualizar a cópia local.
Não sei o que alterei git status + git diff Revisar as alterações.
Commit não aparece no GitHub git push Publicar os commits.
403 / permission denied Parar e chamar o professor Verificar permissões.
PR com destino incorreto Conferir base/compare Garantir feature → develop.
PR pediu correção Corrigir na mesma branch e git push Atualizar o PR existente.
Conflito de merge git status Identificar os arquivos em conflito.

10. E se a porta 5000 estiver ocupada?

Este problema não é um erro do Git. Ele pertence ao ambiente de execução do Flask. Por isso, o procedimento detalhado está no Roteiro de Desenvolvimento 30/09 → Situações comuns.

Como referência, o diagnóstico começa com: 

lsof -i :5000

A documentação do roteiro explica como identificar o PID, utilizar kill PID, verificar novamente e, se necessário, utilizar kill -9 PID.

11. E se houver conflito?

Conflito acontece quando o Git não consegue decidir automaticamente como combinar duas alterações. Isso é comum quando dois grupos alteram a mesma linha ou região do mesmo arquivo.

O procedimento é identificar o arquivo, comparar as versões, resolver o conteúdo, testar novamente, criar um commit de resolução e atualizar o Pull Request.

Importante: conflito não significa que o projeto foi perdido. Significa que o Git precisa de uma decisão humana sobre como combinar as alterações.

12. Integração final

Depois que os Pull Requests forem revisados e integrados em develop, será realizado um teste integrado da aplicação.

O fluxo conceitual é:

feature branches
      ↓
   Pull Requests
      ↓
    develop
      ↓
 teste integrado
      ↓
      main
      ↓
 versão estável

A main permanece como referência da versão principal do produto.

⭐ Regra de ouro

Leia a mensagem, diagnostique o problema e só depois execute a correção. Aprender Git significa também aprender a interpretar o que o Git está informando.
