Roteiro de Desenvolvimento — 30/09

Guia completo e didático para desenvolver uma funcionalidade, trabalhar com Git e integrar a alteração ao repositório do LOGIEXPRESS.

RAD Python • Git • GitHub

🎯 Objetivo da prática

Você fará o trabalho como uma equipe de desenvolvimento de software. A aplicação LOGIEXPRESS já está funcionando. Sua tarefa é partir de uma versão existente, criar uma branch própria, desenvolver uma nova funcionalidade, testar, registrar as alterações com Git, publicar sua branch no GitHub e abrir um Pull Request para a branch develop.

Importante: a main representa a versão principal do produto e não deve ser utilizada diretamente para o desenvolvimento das funcionalidades da prática.

1. Comece pelo projeto existente

O primeiro passo não é sair alterando o código. Antes de desenvolver, você precisa garantir que está trabalhando sobre a versão mais atual da develop.

Regra da prática: primeiro sincronize, depois crie sua branch e somente então comece a alterar os arquivos.
2. Sincronize a branch develop

Abra o terminal do Codespace e execute os comandos abaixo. Execute um comando por vez e observe o resultado. 

git fetch origin
git checkout develop
git pull origin develop
git fetch origin

Consulta o repositório remoto e atualiza as referências locais. Não altera seus arquivos de trabalho.

git checkout develop

Muda para a branch local develop.

git pull origin develop

Traz as alterações mais recentes de origin/develop para sua branch local.

Confira: se o Git informar que sua branch está atualizada, você pode continuar.
3. Crie sua branch de funcionalidade

Cada grupo deve possuir uma branch própria. O nome deve indicar claramente a funcionalidade que será desenvolvida.

Exemplo para o desafio Manutenção de veículos: 

git checkout -b feature/manutencao-veiculos

Outros exemplos: 

git checkout -b feature/controle-combustivel
git checkout -b feature/gestao-ocorrencias
git checkout -b feature/controle-sla
git checkout -b feature/controle-estoque
git checkout -b feature/timeline-entrega

Depois confirme em qual branch você está: 

git branch
A branch marcada com * deve ser a sua feature/....
4. Saiba exatamente quais arquivos podem ser alterados

🗂️ Mapa prático dos arquivos

Arquivo / pasta Quando alterar? O que normalmente entra aqui?
app.py Quase todas as novas funcionalidades Modelos SQLAlchemy, regras, consultas e rotas Flask.
templates/ Quando a funcionalidade precisa de telas HTML, formulários, tabelas, cards e Jinja2.
static/style.css Quando for necessário ajustar o visual Espaçamento, cards, tabelas, cores e responsividade.
templates/base.html Quando for necessário adicionar uma entrada ao menu Links de navegação do sistema.
tests/ Quando houver teste automatizado Testes das rotas e regras principais.
Atenção: não altere arquivos que não tenham relação com sua funcionalidade. Quanto menor e mais organizado for o conjunto de alterações, mais fácil será revisar e integrar o Pull Request.
5. Exemplo completo — Manutenção de veículos

O exemplo abaixo mostra a lógica de desenvolvimento. Ele não deve ser simplesmente copiado sem entendimento. A equipe deve adaptar os nomes, campos e regras à funcionalidade escolhida.

5.1 Criar o modelo no app.py

Uma manutenção precisa estar relacionada a um veículo. Um modelo simplificado poderia ser: 

class Manutencao(db.Model):
    id = db.Column(db.Integer, primary_key=True)
    veiculo_id = db.Column(
        db.Integer,
        db.ForeignKey("veiculo.id"),
        nullable=False
    )
    data = db.Column(db.Date, nullable=False)
    tipo = db.Column(db.String(50), nullable=False)
    descricao = db.Column(db.String(255), nullable=False)
    custo = db.Column(db.Numeric(12, 2), nullable=False)
    status = db.Column(db.String(30), default="ABERTA")

    veiculo = db.relationship("Veiculo")
O que esse código representa? A classe representa uma tabela no banco. Cada atributo representa uma coluna. veiculo_id cria a relação entre a manutenção e o veículo.

5.2 Criar uma rota Flask 

@app.route("/manutencoes")
def manutencoes():
    registros = Manutencao.query.order_by(
        Manutencao.data.desc()
    ).all()

    return render_template(
        "manutencoes/list.html",
        registros=registros
    )

Essa rota consulta os dados e envia o resultado para uma página HTML.

5.4 Teste a navegação

Depois de criar a rota e o template, teste a aplicação no navegador. Se o endereço for /manutencoes, a rota precisa existir e o template precisa estar no caminho esperado.

Regra importante: antes de pensar em Git, faça a funcionalidade funcionar. Depois registre e publique o resultado.
6. Teste antes de fazer o commit

Execute a aplicação como você fez no dia 29/09: 

python app.py

Depois abra a aplicação pelo navegador e teste:

  • menu;
  • rota criada;
  • formulário;
  • cadastro;
  • edição;
  • exclusão, quando existir;
  • validações;
  • mensagens de erro e sucesso;
  • visualização em diferentes tamanhos de tela.

Se o projeto possuir testes automatizados para a funcionalidade, execute também: 

pytest -q
7. Veja exatamente o que foi alterado

Primeiro:

git status

O Git mostrará arquivos modificados, novos arquivos ou arquivos removidos.

Depois, veja as diferenças:

git diff

Quando estiver seguro de que as alterações pertencem à sua funcionalidade: 

git add .
Por que conferir? O comando git add . prepara todas as alterações do diretório. Por isso, git status e git diff são importantes para evitar enviar arquivos que não fazem parte do seu desafio.
8. Crie o commit

Registre a alteração com uma mensagem clara: 

git commit -m "Implementa manutenção de veículos"

Exemplos: 

git commit -m "Implementa controle de combustível"
git commit -m "Implementa gestão de ocorrências"
git commit -m "Implementa controle de SLA"
git commit -m "Implementa timeline de entrega"
Commit não é push. O commit registra a versão no histórico local do Git. O push publica essa versão no GitHub.
9. Publique sua branch no GitHub

Na primeira publicação da branch, utilize: 

git push -u origin feature/manutencao-veiculos

Depois disso, novos pushes dessa mesma branch podem ser feitos com: 

git push
Erro 403 / permission denied? Isso normalmente significa que sua conta não possui permissão de escrita no repositório do professor. Nesse caso, pare e informe o professor; não tente contornar a permissão.
O objetivo do push é publicar sua branch. A integração com develop acontece depois, por meio do Pull Request.
10. Pull Request → revisão → integração

10.1 Criar o Pull Request

Depois do git push, abra o GitHub e localize sua branch. Clique para criar um Pull Request.

O destino deve ser: 

base: develop
compare: feature/manutencao-veiculos

Título sugerido: 

Implementa manutenção de veículos

No corpo do Pull Request, explique:

  • qual problema foi resolvido;
  • qual funcionalidade foi criada;
  • quais arquivos foram alterados;
  • como a funcionalidade foi testada;
  • se existe algum ponto que precisa de atenção.

10.2 O que acontece depois?

O Pull Request será revisado. Se houver correções solicitadas, você volta para sua branch, altera o código, testa novamente, faz outro commit e executa: 

git add .
git commit -m "Corrige validação da manutenção"
git push

O mesmo Pull Request será atualizado automaticamente.

10.3 Integração

Depois da aprovação, o professor fará a integração da branch em develop. A branch main permanece reservada para a versão principal do produto.

Você concluiu o ciclo: branch → desenvolvimento → teste → commit → push → Pull Request → revisão → merge.

🛠️ Situações comuns — o que fazer quando algo dá errado?

Durante o desenvolvimento, mensagens de erro e avisos são normais. O objetivo é aprender a interpretar a mensagem, diagnosticar a causa e executar o procedimento correto.

🔴 Situação 1 — A porta 5000 já está em uso

Isso acontece quando outro processo já está executando o Flask na porta 5000, por exemplo, quando python3 app.py foi iniciado novamente sem encerrar a execução anterior. 

Address already in use
Port 5000 is in use by another program.

1. Descubra quem está usando a porta:

lsof -i :5000

Localize o PID apresentado. Exemplo: 

python3  6383
python3  6417

2. Tente encerrar os processos identificados:

kill 6383 6417
Atenção: os números acima são apenas exemplos. Use os PIDs mostrados pelo seu próprio lsof -i :5000. Não copie os PIDs deste exemplo.

3. Confirme se a porta foi liberada:

lsof -i :5000

Se o comando não retornar nenhuma linha, a porta está livre. Nesse caso, vá para o passo 5.

4. Se o processo continuar ativo, force o encerramento:

kill -9 6383 6417
Use kill -9 somente quando necessário. Esse comando força o encerramento do processo. No laboratório, utilize-o apenas nos PIDs que você identificou como responsáveis pela execução do Flask.

Depois confirme novamente: 

lsof -i :5000

Se não aparecer nenhuma linha, a porta 5000 está livre.

5. Inicie novamente a aplicação:

python3 app.py
Fluxo de diagnóstico:
python3 app.py → porta ocupada → lsof -i :5000 → identificar PID → kill PID → verificar novamente → se necessário kill -9 PID → verificar → python3 app.py

🔵 Situação 2 — Não sei em qual branch estou

git branch

A branch marcada com * é a branch ativa. Antes de alterar arquivos, confirme que você está na sua feature/....

🟡 Situação 3 — Minha develop está desatualizada

Atualize a branch antes de criar uma nova funcionalidade:

git fetch origin
git checkout develop
git pull origin develop

🟠 Situação 4 — Não sei o que alterei

Primeiro veja os arquivos modificados:

git status

Depois confira exatamente as diferenças:

git diff
Use esses comandos antes de git add . para saber o que será registrado.

🟣 Situação 5 — Fiz commit, mas não aparece no GitHub

commit registra a alteração localmente. push publica a branch no GitHub. 

git status
git push

🔴 Situação 6 — Apareceu 403 ou permission denied

remote: Permission to ... denied
fatal: unable to access ...
Pare e informe o professor. A conta utilizada pode não possuir permissão de escrita no repositório ou branch. Não tente contornar a permissão.

🟤 Situação 7 — O Pull Request está com destino errado

Para a prática, confira:

base: develop
compare: feature/manutencao-veiculos
O fluxo esperado é feature → Pull Request → develop. Não utilize main como destino da atividade.

🟢 Situação 8 — O professor pediu uma correção no Pull Request

Continue na mesma branch. Não crie outra branch apenas para corrigir o código. 

git status
git diff
git add .
git commit -m "Corrige validação da funcionalidade"
git push

O Pull Request existente será atualizado automaticamente.

⚠️ Situação 9 — Apareceu um conflito no Git

Primeiro descubra quais arquivos estão envolvidos: 

git status

Se houver conflito, abra os arquivos indicados no VS Code e analise as versões apresentadas. Se não entender o conflito, pare e peça orientação ao professor antes de continuar.

🏁 O exercício terminou. E agora?

Terminar a funcionalidade não significa terminar a atividade. Depois de desenvolver e testar, o grupo precisa preparar o trabalho para ser entregue, revisado e integrado ao projeto.

1. Faça a última rodada de testes

Antes de entregar, execute a aplicação e teste a funcionalidade no navegador. Se o projeto possuir testes automatizados, execute-os também. 

python3 app.py

Em outro terminal, se necessário:

python3 -m pytest
Resultado esperado: a funcionalidade deve funcionar no navegador e os testes automatizados devem passar antes da entrega.

2. Confira exatamente o que será entregue

git status
git diff

O git status mostra os arquivos modificados. O git diff permite revisar o conteúdo alterado.

Antes do commit: verifique se você não alterou arquivos que não fazem parte do seu desafio.

3. Registre a funcionalidade com commit

git add .
git commit -m "Implementa manutenção de veículos"

Substitua a mensagem pelo nome da funcionalidade desenvolvida pelo seu grupo.

4. Envie a branch para o GitHub

Se for o primeiro envio dessa branch: 

git push -u origin feature/manutencao-veiculos

Depois que a branch já estiver vinculada ao GitHub, os próximos envios podem utilizar: 

git push
Atenção: substitua feature/manutencao-veiculos pelo nome da branch do seu grupo.

5. Crie o Pull Request

Depois do push, abra o repositório no GitHub e crie um Pull Request. Confira cuidadosamente: 

base: develop
compare: feature/manutencao-veiculos

O título deve identificar claramente a funcionalidade. Exemplo: 

Implementa manutenção de veículos

Na descrição do Pull Request, informe pelo menos:

  • qual funcionalidade foi desenvolvida;
  • quais arquivos principais foram alterados;
  • como a funcionalidade foi testada;
  • se existe alguma limitação ou ponto que precisa de atenção.

6. Depois de abrir o Pull Request, o trabalho ainda não acabou

O professor ou responsável pela integração poderá revisar o código e solicitar alterações. Se isso acontecer, continue trabalhando na mesma branch. 

# corrigir o código

git status
git diff
git add .
git commit -m "Corrige validação da funcionalidade"
git push

O Pull Request existente será atualizado automaticamente. Não é necessário criar outro PR para cada correção.

7. Quando o Pull Request for aprovado

Após a revisão e aprovação, a funcionalidade poderá ser integrada à develop. O grupo deve aguardar a integração antes de considerar a entrega concluída.

Fluxo de entrega:
feature/grupo → git push → Pull Request → revisão → correções, se necessárias → merge em develop

8. Após a integração: atualizar sua cópia local

Depois que a funcionalidade estiver integrada, volte para a develop e atualize sua cópia local: 

git checkout develop
git pull origin develop

Isso garante que seu ambiente local contenha a versão integrada mais recente do projeto.
